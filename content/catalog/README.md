# Catalog Canonical Format

This folder is the canonical V1 catalog source inside the repo.

It exists to replace workbook-first editing for large-scale catalog growth, while
keeping the workflow explicit:

1. machine generates seeds,
2. humans apply targeted overrides,
3. a build step produces final import-ready JSON.

## Files

### Seeds

- `catalog-meta.json`
  - metadata for the current generated seed snapshot
- `typefaces-core.seed.json`
  - baseline editorial/core records generated from trusted local sources
- `font-runtime-assets.seed.json`
  - baseline runtime asset records generated from the manifest and mirrored fonts
- `expert-answer-keys.seed.json`
  - baseline Expert answer records generated from display names

### Overrides

- `overrides/typefaces-core.overrides.json`
  - human editorial corrections for typeface core records
- `overrides/font-runtime-assets.overrides.json`
  - human runtime-asset corrections or additions
- `overrides/expert-answer-keys.overrides.json`
  - human Expert-answer corrections or additions
- `overrides/README.md`
  - merge rules and examples

### Batches

- `batches/README.md`
  - curated promotion batches selected from larger candidate queues
- `batches/google-fonts-batch-001.selection.json`
  - first selected lot from the Google Fonts snapshot
- `batches/google-fonts-batch-001/`
  - built review packet for that batch
- `batches/google-fonts-pilot-top-10.selection.json`
  - compact pilot lot used to validate promotion workflow on a high-value subset
- `batches/google-fonts-pilot-top-10/`
  - built review packet for that 10-family pilot batch

### Built outputs

- `catalog-build-meta.json`
  - metadata and counts for the latest merged catalog build
- `typefaces-core.json`
  - merged typeface catalog, ready for import
- `font-runtime-assets.json`
  - merged runtime asset catalog, ready for import
- `expert-answer-keys.json`
  - merged Expert answer catalog, ready for import

## Format rules

1. JSON files are machine-first.
2. No legend rows, notes rows, blank rows, or visual-only markers inside `records`.
3. Human notes must live in:
   - `meta.notes`
   - record-level `notes` arrays
   - docs in `docs/`
4. Field names use snake_case.
5. `structural_signature` is stored as a JSON object, not a stringified JSON blob.
6. Seed files are relaunchable machine output.
7. Human changes belong in `overrides/`, not directly inside the seed files.
8. Final importable files are generated by the build step.

### typefaces-core.seed.json
Each record represents one typeface and should include:

- `typeface_slug`

- `sub_category`
- `visual_cluster_id`
- `dreyfus_tier`
- `difficulty_base`
- `rarity_tag`
- `activation_status`
- `font_source`
- `is_variable_font`
- `year_tag`
- `weight_structure`
- `contrast_profile`
- `aperture_profile`
- `structural_signature`
- `release_year`
- `designer`
- `foundry`
- `license_type`
- `license_url`
- `fallback_stack`
- `expert_enabled`
- `min_mode`
- `qa_status`
- `notes`

### font-runtime-assets.seed.json
Each record represents the primary runtime asset for one typeface.

- `typeface_slug`
- `file_role`
- `font_format`
- `weight`

- `source_path`
- `runtime_path`
- `file_size_bytes`
- `sha256_hash`
- `runtime_status`
- `asset_origin`
- `verified_at_utc`
- `notes`

### expert-answer-keys.seed.json
Each record represents one accepted Expert answer.

- `typeface_slug`
- `answer_text`
- `answer_normalized`
- `is_canonical`
- `locale`
- `qa_status`
- `notes`

## Workflow

1. Rerun the generator script.
2. Review generated drafts and notes.
3. Add targeted human changes in `overrides/`.
4. If candidate queues are large, create a curated batch.
5. Run the catalog build step.
6. Import the merged JSON files into DB.
7. Keep Excel as optional review/export, not the only source of truth.

## Generator

The initial generator for these files is:

- `scripts/generate_catalog_seed.py`

It reads the current source Excel + font manifest and emits the canonical seed files in this folder.

## Builder

The merge/build step is:

- `scripts/build_catalog.py`

It reads the seed files plus the override files and emits final merged JSON files.

## Importer

The DB import step is:

- `scripts/import_catalog_json.py`

It reads the final built JSON files and upserts them into PostgreSQL.

Current V1 behavior:

- `typefaces-core.json` is imported fully
- `expert-answer-keys.json` is imported fully
- `font-runtime-assets.json` imports only DB-compatible runtime rows
- `system_local` runtime records are intentionally skipped until they are replaced
  by mirrored libre assets

## Promotion audit

Promotion readiness is now audited by:

- `scripts/audit_catalog_promotion.py`

It classifies a candidate queue or review batch into:
- already known,
- blocked by editorial gaps,
- blocked by runtime preparation,
- or ready for promotion.

Current usage examples:
- `content/catalog/batches/google-fonts-pilot-top-10/promotion-audit.json`
- `content/catalog/candidates/google-fonts-snapshot/promotion-audit.json`

## Runtime preparation

Runtime preparation from candidate/review files is handled by:

- `scripts/prepare_catalog_runtime.py`

It converts or copies a primary source file to a public WOFF2 asset and emits:
- `font-runtime-assets.prepared.json`
- `runtime-prep-report.json`

Current usage example:
- `content/catalog/batches/google-fonts-pilot-top-10/runtime-prep/`

## Promotion staging

Semi-automatic promotion staging is handled by:

- `scripts/stage_catalog_promotion.py`

It fills safe fields automatically and isolates the remaining editorial review
fields before main-catalog promotion.

Current usage example:
- `content/catalog/batches/google-fonts-pilot-top-10/promotion-stage/`

## Editorial review templates

Editorial review templates are generated by:

- `scripts/generate_editorial_review_template.py`

It emits:
- `editorial-review-template.json`
- `editorial-review-template.csv`

Current usage examples:
- `content/catalog/batches/google-fonts-pilot-top-10/editorial-review/`
- `content/catalog/batches/google-fonts-batch-001/editorial-review/`

The template keeps only the remaining human-review fields:
- `sub_category`
- `visual_cluster_id`
- `dreyfus_tier`
- `difficulty_base`
- `rarity_tag`
- `year_tag`
- `weight_structure`
- `contrast_profile`
- `aperture_profile`
- `structural_signature`

## Reviewed promotion builder

Promotion fragments from a completed editorial review are built by:

- `scripts/build_reviewed_promotion.py`

It validates that:
- runtime is already ready in staging,
- every editorial field is filled,
- `review_status=approved`,
- `structural_signature` is a complete object.

It writes:
- `promotion-validation-report.json`
- and, only if validation passes:
  - `typefaces-core.promotion-ready.json`
  - `font-runtime-assets.promotion-ready.json`
  - `expert-answer-keys.promotion-ready.json`

Important:
- this script does **not** merge anything into the main catalog automatically
- it produces promotion-ready fragments only

## Promotion pipeline orchestrator

The end-to-end promotion-prep workflow can be run by:

- `scripts/run_catalog_promotion_pipeline.py`

It chains:
1. promotion audit,
2. runtime preparation,
3. semi-automatic promotion staging.

The current implementation also produces a post-staging audit so the remaining
blockers are explicit after runtime preparation.

## Mass catalog promotion

Large-scale catalog-only promotion is handled by:

- `scripts/mass_catalog_candidates.py`
- `scripts/merge_catalog_override_fragment.py`
- `scripts/import_massive_font_source.py --include-known`

This lane is intentionally different from reviewed batch promotion.

It is used when we want to:
- make the catalog much heavier quickly,
- add many real typefaces into `typefaces_core`,
- keep them inactive by default,
- avoid mirroring thousands of new runtime assets immediately.

Current behavior:
- new typefaces are added with `activation_status=false`
- `expert_enabled=false`
- `qa_status=review`
- new Expert answer keys are added in `review`
- no new main runtime assets are added in this step
- `year_tag` is now derived from snapshot metadata (`date_added`) when available

External metadata sync:
- `scripts/sync_google_fonts_api.py` can query the official Google Fonts Developer API
- it produces local sync reports under `content/catalog/google-api-sync/`
- it is used for watch / verification / prioritization only
- it does not replace the snapshot pipeline or the self-hosted runtime subset

Merge behavior:
- `merge_catalog_override_fragment.py` is now non-destructive by default
- existing reviewed/manual overrides are preserved
- untouched mass-catalogued `typefaces_core` review records can still be refreshed safely in `smart` mode
- `expert_answer_keys` review records are preserved unless an explicit destructive merge mode is requested

This means:
- catalog size can grow much faster than runtime-ready product size
- the game still only uses the reviewed runtime-ready subset
- editorial refinement can happen later without blocking catalog growth
